SLIDE 2 - Problem, Scope, Exclusions & Key Domain Terms

Problem:
The system needs to handle confirming an existing seat reservation for a cinema show. The key behaviour is to confirm a pending reservation and, as a follow-up, reserve the corresponding seat in that show.

Scope (What’s Included):
- Confirm an existing seat reservation (Main Use Case)
- Reserve the corresponding seat in the Show after the reservation is confirmed (Connected Follow-Up Use Case)
- Exactly 6 business rules (BR1–BR6) as required
- Two Aggregates (Reservation and Show), one Domain Event, one Application Service
- In-memory persistence only
- 8 automated tests (T1–T8) with TDD evidence

Exclusions (Outside Scope):
- Reservation creation (not part of the two use cases)
- Full booking/management system
- Web interface, database, deployment, microservices, message brokers
- Payment, authentication, or reporting

Key Domain Terms:
- Reservation – An identified request for a seat in a specific Show (starts in PENDING, can become CONFIRMED)
- Show – Cinema show (has a start time and a collection of ShowSeats)
- ShowSeat – A seat in a Show (can be AVAILABLE or RESERVED)
- SeatNumber – A value identifying a seat (row letter A–Z + position 1–50)
- Customer – The person holding/reserving seats
- Domain Event – A record of something important that happened in the Domain (used to trigger follow-up action)
- Aggregate Root – The main object that protects the invariant of an Aggregate (Reservation, Show)
- Domain Service – Encapsulates domain logic that spans more than one concept/aggregate (BR4)
- Repository – Abstraction for retrieving/storing aggregates (Application layer port; Infrastructure implementation)

SLIDE 3 - BR1–BR6: Statement, Responsible Component & Violation Outcome

| BR | Rule Type | Rule Statement | Responsible Component | Violation Outcome |
|---|---|---|---|---|
| BR1 | Value Rule | A SeatNumber is valid only when it contains one row letter from A–Z followed by a seat position from 1–50. | Value Object – SeatNumber | InvalidSeatNumberError |
| BR2 | Identity/State Rule | A Reservation starts in PENDING state and may transition to CONFIRMED only from PENDING. | Entity/Aggregate Root – Reservation | InvalidReservationStateError |
| BR3 | Invariant Rule | Within one Show, a ShowSeat may be allocated to at most one Reservation. | Aggregate Root – Show (and ShowSeat internal) | SeatAlreadyReservedError |
| BR4 | Cross-Concept Rule | A Reservation is eligible for confirmation only when the Show has not started AND the customer has fewer than four confirmed seats for that Show. | Domain Service – ReservationEligibilityService | ReservationNotEligibleError |
| BR5 | Follow-Up Rule | When a Reservation is confirmed, a ReservationConfirmed Domain Event requests the Show to reserve the SeatNumber. | Reservation (raises event) + ReservationConfirmedHandler (handles event) + EventDispatcher | If Show rejects allocation, confirmation is not persisted |
| BR6 | Lookup Rule | A Reservation must already exist before confirmation can proceed. | ReservationRepository + ConfirmReservationService (Application Service) | ReservationNotFoundError |

SLIDE 4 - Value Object & Entities (Linked to BR1 and BR2)

Value Object – SeatNumber (BR1)
- Small immutable value with no separate identity (identity is its value).
- Enforces BR1 in its constructor (__post_init__): validates format [A–Z][1–50].
- Reason for VO: seat numbers are interchangeable by value and don’t change identity over time.

Entities
- Reservation (Entity / Aggregate Root) – BR2
  - Identity: reservation_id
  - States: PENDING, CONFIRMED
  - confirm() enforces BR2 (only PENDING -> CONFIRMED). Raises ReservationConfirmed event on confirmation (BR5).
- ShowSeat (Entity inside Show Aggregate) – part of BR3
  - Identity: seat_number (within a Show)
  - Tracks status (AVAILABLE/RESERVED), reservation_id, customer_id
  - Internal _reserve() to protect aggregate boundary (only Show may change it)

Link: BR1 enforced by Value Object. BR2 enforced by Reservation Entity state transition.

SLIDE 5 - Aggregates A & B: Roots, Contents & Invariants (Linked to BR3)

Aggregate A – Reservation (Aggregate Root)
- Root: Reservation
- Contents: Owns its state and domain events (_events)
- Purpose: Manages reservation lifecycle (BR2). Raises BR5 event on confirmation
- Identity: reservation_id

Aggregate B – Show (Aggregate Root)
- Root: Show
- Contents: Collection of ShowSeat entities (child entities inside the aggregate)
- Invariant (BR3): “Within one Show, a ShowSeat may be allocated to at most one Reservation”
  - Enforced by Show.reserve_seat(): checks seat is not already RESERVED before allocating
  - ShowSeat._reserve() is aggregate-internal (cannot be called from outside Show)
- Identity: show_id
- Also supports BR4: confirmed_seat_count_for(customer_id) answers how many seats a customer holds in this Show

Aggregate Boundaries: Aggregates do not hold references to each other. Communication across boundaries happens only via Domain Event (BR5) carrying plain data.

SLIDE 6 - Domain Service (BR4) & Factory Decision

Domain Service – ReservationEligibilityService (BR4)
- Used because BR4 is a cross-concept rule: it needs information from both Reservation and Show (spans two aggregates). It does not naturally belong to one entity.
- Stateless, with zero collaborators (no repository). Takes only (reservation, show, current_time)
- Logic: 
  - If current_time >= show.start_time -> reject (Show not started requirement)
  - If show.confirmed_seat_count_for(customer_id) >= 4 -> reject (customer has < 4 confirmed seats for that Show)
- Enforces BR4 cleanly while keeping Domain layer depending only on Domain objects.

Factory Decision – Show.create()
- Used: Yes, for Show.
- Reason: Building the full seat map (rows/seats_per_row, all seats start AVAILABLE) is a construction rule, not ad-hoc assembly. Centralises creation and prevents invalid/incomplete Show construction.
- Other objects: Reservation is fully described by its constructor (reservation_id, customer_id, show_id, seat_number). Adding a Factory would add unnecessary indirection.
- Conclusion: Factory justified for Show only.

SLIDE 7 - Repositories: Abstractions, In-Memory Implementations & What They Store

Repository Abstractions (Application Layer – Ports)
- ReservationRepository (Abstract Base Class)
  - get_by_id(reservation_id) -> Optional[Reservation]
  - save(reservation) -> None
  (Port defined where used by Application; implemented in Infrastructure)
- ShowRepository (Abstract Base Class)
  - get_by_id(show_id) -> Optional[Show]
  - save(show) -> None

In-Memory Implementations (Infrastructure Layer – Adapters)
- InMemoryReservationRepository implements ReservationRepository
  - Stores Reservations in a dict keyed by reservation_id
  - Uses deepcopy on read and save (returns/stores copies) to avoid leaking in-memory state
- InMemoryShowRepository implements ShowRepository
  - Stores Shows (and their ShowSeats) keyed by show_id
  - Uses deepcopy on read and save

What Each Stores:
- ReservationRepository store: Reservation aggregates (by ID), including status and recorded domain events (not dispatched here)
- ShowRepository store: Show aggregates (by ID) with their collection of ShowSeats and their states (AVAILABLE/RESERVED, holder info)

Note: Repositories are in Application layer as abstractions (ports), implementations in Infrastructure. Domain has no dependency on repositories.

SLIDE 8 - Clean Architecture Diagram & Dependencies

Layers: Domain, Application, Infrastructure, Interface

Dependencies (Inward-Only):
- Domain → (nothing outside Domain)
- Application → Domain
- Infrastructure → Application, Domain
- Interface (CLI) → Application, Domain, Infrastructure

Explanation:
- Domain: Core business (Entities, Value Objects, Aggregates, Domain Services, Domain Events). Pure, no technical dependencies.
- Application: Use cases/orchestration. Contains Application Service, DTOs, and repository abstractions (ports). Depends only on Domain.
- Infrastructure: Technical adapters. Provides in-memory repository implementations. Depends on Application and Domain.
- Interface: Entry point (CLI). Minimal composition root – wires dependencies (Dependency Injection). Depends on Application/Domain/Infrastructure.

Dependency Check: python scripts/check_dependencies.py → “OK: all imports point inward.”

Key Point: The Domain layer has zero collaborators (no repositories, no dispatcher, no infrastructure). Dependencies always point inward toward Domain.

SLIDE 9 - Main Application Service, Input/Output DTOs & Dependency Injection

Main Application Service: ConfirmReservationService
- Purpose: Orchestrate the “Confirm a Seat Reservation” use case (coordinate, don’t contain core business rules)
- Responsibilities: BR6 lookup (Reservation must exist), load Show, call BR4 (Domain Service), call BR2 (Reservation.confirm()), dispatch BR5 events, persist only on success, handle DomainError → return failure without saving

Input DTO: ConfirmReservationInput
- request.reservation_id – identifies the reservation to confirm

Output DTO: ConfirmReservationOutput
- reservation_id, status, success, message

Dependency Injection (DI):
- Dependencies are injected from outside the service (via constructor):
  - reservation_repository: ReservationRepository (abstraction)
  - show_repository: ShowRepository (abstraction)
  - eligibility_service: ReservationEligibilityService (Domain Service)
  - event_dispatcher: EventDispatcher (in-process)
  - clock (optional): provides current time for BR4
- The Composition Root is Interface/CLI (build_service()): creates concrete implementations (in-memory repos, dispatcher, handler registration) and injects them into ConfirmReservationService.
- This keeps Application decoupled from Infrastructure and allows swapping implementations.

Location: src/application/services/confirm_reservation_service.py

SLIDE 10 - BR5 Domain Event Flow (Aggregate A → Event → Handler → Aggregate B)

Definitions (to explain clearly):
- DTO (Data Transfer Object): Simple objects that carry data between layers (input/output). They don’t contain business logic.
- Domain Event: A record of something important that happened in the Domain (immutable, carries plain data only). Used for cross-aggregate communication without coupling.
- Layer Supertype: A common base class in a layer (here DomainEvent for domain events). Allows code (e.g. EventDispatcher) to work against an abstraction, not concrete event types.
- Event Dispatcher: In-process component that routes Domain Events to registered handlers by event type (dispatches events when asked). It does not decide business rules.
- Handler: A component that reacts to a Domain Event (application/domain coordination). It loads aggregates, calls domain methods, and saves. The handler itself makes no business decisions.
- pull_events(): Method on an aggregate (Reservation) that returns all recorded domain events and clears them (emits events out without leaking internal list).
- Dispatching: The act of sending collected events to handlers (done in Application layer, after domain behaviour happens).
- Load–Call–Save: Pattern used by handlers: load aggregate from repository → call domain behaviour (method) → save aggregate back via repository. Keeps business rules inside Domain.

Event: ReservationConfirmed (extends DomainEvent). Carries only: reservation_id, customer_id, show_id, seat_number (no aggregate references).

Flow:
1. Request -> ConfirmReservationInput -> Application Service
2. Aggregate A (Reservation).confirm() while PENDING -> becomes CONFIRMED. Records ReservationConfirmed event (BR2 + BR5)
3. reservation.pull_events() returns and clears events
4. EventDispatcher.dispatch(events) – dispatching by event type
5. ReservationConfirmedHandler.handle(event): load Aggregate B (Show) via repository -> show.reserve_seat(seat_number, reservation_id, customer_id) (BR3) -> save Show
Key: Aggregates don’t call each other. Aggregate records events; Application dispatches. Handler uses load–call–save only. DomainEvent is the Layer Supertype.

SLIDE 13 - Complete Use Case Walkthrough (Simple)

CLI demo: python -m src.interface.cli R001 → “R001: CONFIRMED - Reservation confirmed and seat reserved”

Initial state (seeded): S001 has seats A1,A2 (starts in +2 hours). R001 is for C001,S001,A1 and starts as PENDING.

Steps:
1. Input: ConfirmReservationInput(reservation_id='R001')
2. Load Reservation (BR6): must exist. Load Show for that reservation
3. Check eligibility (BR4): Show not started and customer has < 4 confirmed seats in this Show
4. Confirm Reservation (BR2): reservation.confirm() → PENDING becomes CONFIRMED. Records ReservationConfirmed event (BR5)
5. Dispatch events (BR5 → BR3): EventDispatcher sends event to Handler. Handler loads Show, calls show.reserve_seat(A1, R001, C001) (BR3 invariant enforced)
6. Save: Reservation saved only after successful event handling

Result (Success – T7): R001 is CONFIRMED. Seat A1 in S001 becomes RESERVED. Others unchanged.

Failure case (T8): If seat already RESERVED, Show.reserve_seat() raises SeatAlreadyReservedError (DomainError). Service catches it → returns success=False, Reservation stays PENDING, Show unchanged, nothing saved.

SLIDE 14 - Design Choice We Changed (Simple Explanation)

Main Change: BR4 Domain Service must NOT depend on a repository

Before (what we had):
- ReservationEligibilityService took ReservationRepository and called count_confirmed_seats(customer_id, show_id)
- This meant the Domain layer depended on storage (persistence). Even if injected (no import crossing), it’s still a dependency.
- Our dependency checker only checked imports, so it didn’t catch this.

Why we changed it:
- Clean Architecture: Domain must depend only on Domain, not on Application/Infrastructure
- The info “how many confirmed seats this customer has in this Show” already lives inside the Show aggregate
- Better to keep aggregates owning their own state

Fix:
- Added customer_id/reservation_id to ShowSeat
- Added Show.confirmed_seat_count_for(customer_id) to count from aggregate state
- Made ReservationEligibilityService stateless with zero collaborators – takes only (reservation, show, current_time)
- Removed count_confirmed_seats() from repository port and in-memory implementation
- ReservationConfirmed now carries customer_id so handler records holder correctly

Result:
- Dependencies now point fully inward (Domain → nothing outside). Verified: python scripts/check_dependencies.py → OK
- Behaviour unchanged – all BR4 tests still pass
- Cleaner, correct DDD/Clean Architecture design
